# ADR-0001 — JARVIS OS Foundation Architecture

- **Status:** Accepted
- **Date:** 2026-09-12
- **Owners:** Project Owner
- **Decision Type:** Foundational Architecture
- **Scope:** Entire system
- **Supersedes:** None

---

# 1. Context

This project aims to build a local-first personal AI agent operating system called **Jarvis OS**.

Jarvis OS is not a chatbot application.

It is a persistent agent runtime capable of:

- interacting through multiple interfaces
- understanding user context
- maintaining long-term memory
- executing tools
- controlling the local computer
- browsing the web
- working with files and code
- delegating complex tasks to specialized AI agents
- running long-running background tasks
- interacting through natural voice
- operating with local AI models when possible
- selectively using premium AI agents when they provide significant value

The system is initially designed for a single-user desktop environment.

Primary hardware:

- NVIDIA RTX 3050
- 8 GB VRAM
- Ryzen 5 5600G
- 32 GB RAM
- webcam
- speakers
- headphones

The system should optimize for this hardware while remaining portable to more powerful hardware in the future.

The project should be practical and incremental.

The architecture must avoid both extremes:

1. a fragile collection of scripts
2. an unnecessarily complex distributed system

The system should start simple but have clear boundaries that allow individual components to evolve independently.

---

# 2. Product Vision

Jarvis OS should behave as a persistent personal agent.

The user should be able to say:

> "Jarvis, open Cursor."

> "Jarvis, what was I working on yesterday?"

> "Jarvis, investigate this while I work."

> "Jarvis, look at my current screen and explain this error."

> "Jarvis, review this repository and fix the problem."

The system should understand:

- current conversation
- recent activity
- relevant memories
- current application
- current project
- available tools
- permissions
- active tasks

Jarvis should prefer action over unnecessary explanation.

Jarvis should not require the user to manually describe context that the system can safely discover.

# 3. Core Design Principles

## 3.1 Local-first

The system should execute locally whenever practical.

Local operations include:

- wake word detection
- voice activity detection
- speech-to-text
- text-to-speech
- simple LLM inference
- embeddings
- memory storage
- file operations
- system operations
- local automation

Cloud AI should be used selectively for:

- complex reasoning
- advanced coding
- difficult research
- advanced vision
- tasks where local models are insufficient

The system must continue providing meaningful functionality without cloud connectivity.

---

## 3.2 Voice is an interface, not the system

Voice must not contain business logic.

The core runtime must be accessible through:

- voice
- desktop UI
- CLI
- API
- future mobile clients
- future messaging interfaces

All interfaces should normalize requests into a common input protocol.

Architecture:

```text
VOICE
UI
CLI
API

   │

   ▼

JARVIS RUNTIME
```

---

## 3.3 Provider independence

The runtime must not depend directly on a specific AI model provider.

The system should support:

- local models
- Claude-based agents
- Codex-based agents
- future providers

Business logic must depend on interfaces.

Example:

```text
LLMProvider
AgentHarness
EmbeddingProvider
VisionProvider
STTProvider
TTSProvider
```

Provider-specific implementations must remain isolated.

---

## 3.4 Deterministic before agentic

The system should not invoke an LLM when deterministic logic is sufficient.

Example:

User:

> "Increase volume."

Preferred execution:

```text
Intent Match
    ↓
System Tool
    ↓
Execute
```

Avoid:

```text
LLM
    ↓
Reasoning
    ↓
Tool Selection
    ↓
Execute
```

LLMs should be used when interpretation or reasoning is required.

---

## 3.5 Context is assembled dynamically

The system must never dump all available information into a prompt.

Context should be selected based on the current task.

Potential context sources:

- conversation
- memory
- active application
- active window
- selected text
- clipboard
- project context
- files
- skills
- available tools

The runtime should retrieve, rank and budget context.

---

## 3.6 Safety boundaries are architectural

Tool permissions must not rely solely on model instructions.

Permissions must be enforced by the execution layer.

Models may request actions.

The permission system decides whether they may execute them.

---

## 3.7 Bounded autonomy

Agents must operate within limits.

Every agent execution should have limits for:

- maximum steps
- maximum duration
- maximum tool calls
- maximum retries
- maximum resource usage

The system must avoid infinite loops and uncontrolled autonomous execution.

---

## 3.8 Observability from the beginning

Every significant execution should be traceable.

The system should record:

- request
- route
- selected model
- selected agent
- tool calls
- task lifecycle
- errors
- latency
- result

Observability is a foundational capability, not a future feature.

# 19. Memory Retrieval

Retrieval should combine:

```text
Semantic similarity

Recency

Importance

Entity relationships
```

Example score:

```text
semantic × 0.5

+

recency × 0.2

+

importance × 0.2

+

entity relevance × 0.1
```

These weights are initial defaults and must be evaluated.

# 34. GPU Resource Management

The GPU is a shared resource.

Consumers include:

```text
STT

LLM

Vision
```

Priority:

```text
1. Active user speech

2. Active user response

3. Vision

4. Background tasks
```

The resource manager should expose:

```typescript
interface ComputeScheduler {
  acquire(job: ComputeJob): Promise<ComputeLease>;

  release(
    lease: ComputeLease
  ): Promise<void>;
}
```

Do not over-engineer this into a distributed scheduler.

A local queue and mutex strategy is sufficient for V1.

# 58. Error Handling

Every failure should be classified.

```text

```

The runtime should not expose internal stack traces directly to voice.

```text

"Terminal execution failed."

"I need permission before continuing."
```

Detailed logs remain available in the dashboard.

# 59. Retry Strategy

Retries should not be automatic for every failure.

Retry only when appropriate.

Examples:

```text
temporary network failure
```

may retry.

```text
permission denied
```

must not retry.

```text
invalid tool input
```

may return the error to the model for correction.

Maximum retries must be bounded.

Important boundaries:

```text

```

```text
Model

≠

```

```text
Model

```

# 62. Architecture Decisions

## ADR Decision A

### Use TypeScript for the main runtime.

Reason:

- existing developer expertise
- strong ecosystem
- shared types
- desktop compatibility
- fast iteration

---

## ADR Decision B

### Use Python for voice and ML services.

Reason:

- ML ecosystem
- CUDA ecosystem
- audio libraries
- STT ecosystem
- TTS ecosystem

---

## ADR Decision C

### Use PostgreSQL + pgvector.

Reason:

- reliable
- familiar
- transactional
- relational
- vector support
- entity relationships

Avoid unnecessary databases.

---

## ADR Decision D

### Use Redis + BullMQ for background tasks.

Reason:

- simple
- TypeScript ecosystem
- enough for V1

---

## ADR Decision E

### Use Docker for sandboxing.

Reason:

- simple
- mature
- sufficient for V1

---

## ADR Decision F

### Use Tauri for desktop.

Reason:

- lightweight
- TypeScript frontend
- native capabilities
- lower resource usage

---

## ADR Decision G

### Use a custom lightweight agent runtime.

Reason:

The project requires:

- custom routing
- permissions
- voice interaction
- local models
- external agent harnesses
- hardware scheduling

The core should remain understandable.

Existing frameworks may be integrated later where useful.

Do not make the entire architecture dependent on a single agent framework.
